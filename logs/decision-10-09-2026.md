# GNSS Acquisition Engine - Design Decisions Summary

## Executive Summary

This document captures all major architectural and implementation decisions made during the development of the FPGA-based GNSS acquisition engine. Each decision includes the rationale, alternatives considered, and trade-offs accepted.

---

## 1. Sampling Rate: 4 MHz (Not 4.096 MHz)

**Decision:** Use 4 MHz sampling rate derived from 100 MHz system clock via integer division (÷25)

**Rationale:**
- 4 MHz is a clean integer division from the 100 MHz ZedBoard oscillator
- Avoids complex MMCM fractional division or additional clock wizards
- 4096 samples at 4 MHz = 1.024 ms, which is acceptable for acquisition (GPS code period is 1.000 ms)
- Simplifies timing closure and reduces jitter

**Alternatives Considered:**
- **4.096 MHz:** Would give exactly 1.000 ms per 4096 samples, but requires fractional clock division (100/4.096 = 24.414), causing Vivado MMCM errors
- **16.368 MHz:** Higher resolution but uses 4× more BRAM and DSP resources

**Trade-offs:**
- ✅ Simple, clean implementation
- ✅ No timing violations
- ⚠️ 2.4% timing error (1.024 ms vs 1.000 ms) - acceptable for acquisition
- ⚠️ Slightly lower code phase resolution

---

## 2. FFT Size: 4096 Points

**Decision:** Use 4096-point FFT for parallel code phase search

**Rationale:**
- 4096 = 2^12, which is optimal for Xilinx FFT IP core efficiency
- Provides 4096 code phase bins (1 chip resolution at 4 MHz sampling)
- Matches the 1ms GPS C/A code period (1023 chips, zero-padded to 4096)
- Industry standard for GPS L1 C/A acquisition

**Alternatives Considered:**
- **2048 points:** Would save ~50% BRAM but reduces code phase resolution to 2 chips
- **8192 points:** Better resolution but doubles BRAM usage and processing time

**Trade-offs:**
- ✅ Maximum FFT IP efficiency (power-of-2)
- ✅ Good code phase resolution (1 chip)
- ⚠️ Requires significant BRAM (~12 BRAM36 for FFT internal buffers)
- ⚠️ 4096 samples must be buffered before processing (adds latency)

---

## 3. Number of PRNs: 16 (Reduced from 32)

**Decision:** Search only 16 PRNs instead of all 32 GPS PRNs

**Rationale:**
- Zynq-7020 has only 140 BRAM36s available
- Storing 32 PRN FFTs required ~128 BRAM36s, causing overutilization (296 BRAM18 > 280 limit)
- Reducing to 16 PRNs cuts ROM usage in half (~64 BRAM36s)
- Real-world GPS receivers typically see only 6-12 satellites at any time

**Alternatives Considered:**
- **Keep 32 PRNs:** Would require larger FPGA (Zynq-7045 with 280 BRAM36s) or time-multiplexing
- **Time-multiplexed ROM:** Load PRNs dynamically from external memory, but adds complexity
- **Reduce FFT size to 2048:** Would save BRAM but sacrifice resolution

**Trade-offs:**
- ✅ Design fits within Zynq-7020 resources (61% BRAM utilization)
- ✅ Still searches enough PRNs for demonstration and most real-world scenarios
- ⚠️ Cannot acquire satellites with PRN > 16
- ⚠️ Future expansion requires code changes or larger FPGA

---

## 4. NCI Frames: 10 (Reduced from 20)

**Decision:** Use 10 frames of non-coherent integration instead of 20

**Rationale:**
- 20ms NCI provides ~13 dB sensitivity gain but uses more BRAM for accumulator
- 10ms NCI provides ~10 dB sensitivity gain (still sufficient for most signals)
- Reduces NCI accumulator BRAM usage by ~50%
- Faster acquisition time (10ms vs 20ms per Doppler bin)

**Alternatives Considered:**
- **20 frames:** Maximum sensitivity but uses more BRAM and takes longer
- **5 frames:** Minimal BRAM but only ~7 dB gain (may miss weak signals)
- **Adaptive NCI:** Dynamically adjust based on signal strength, but adds complexity

**Trade-offs:**
- ✅ Reduces BRAM usage
- ✅ Faster acquisition (10ms per bin vs 20ms)
- ⚠️ 3 dB lower sensitivity than 20ms NCI
- ⚠️ May struggle with very weak signals (< -130 dBm)

---

## 5. Clock Architecture: 100 MHz System + 200 MHz Processing

**Decision:** Use 100 MHz for data I/O and 200 MHz for FFT/processing

**Rationale:**
- 100 MHz matches ZedBoard oscillator (no external clock needed)
- 200 MHz provides 2× processing speed for FFT and complex multipliers
- Allows FFT IP to meet timing at higher throughput
- Clean clock hierarchy: 100 MHz → MMCM → 200 MHz

**Alternatives Considered:**
- **Single 100 MHz clock:** Simpler but FFT processing takes 2× longer
- **Single 200 MHz clock:** Requires external oscillator or fractional division
- **Three clocks (100/200/4 MHz):** More complex but optimal for each domain

**Trade-offs:**
- ✅ Good balance of speed and simplicity
- ✅ FFT IP meets timing at 200 MHz
- ⚠️ Requires clock domain crossing (CDC) between 100 MHz and 200 MHz
- ⚠️ Adds MMCM resource usage (1 of 4 available)

---

## 6. PRN Indexing: 1-Based (Not 0-Based)

**Decision:** Use 1-based indexing for PRN numbers (PRN 1 to PRN 16)

**Rationale:**
- GPS PRNs are natively numbered 1-32 in the ICD (Interface Control Document)
- User expects output like "Best PRN: 1" not "Best PRN: 0"
- Matches simulation testbench expectations
- Simplifies debugging and verification

**Alternatives Considered:**
- **0-based indexing:** More natural for Verilog arrays but confusing for GPS domain
- **Hybrid approach:** 0-based internally, 1-based externally - adds conversion logic

**Trade-offs:**
- ✅ Matches GPS standard and user expectations
- ✅ Easier debugging (PRN 1 = first satellite)
- ⚠️ Requires offset logic in controller (prn_counter starts at 1, prn_sel_out starts at 0 for ROM)
- ⚠️ Slightly more complex state machine

---

## 7. Clock Constraint Ownership: Clocking Wizard IP

**Decision:** Let Clocking Wizard IP auto-generate input clock constraints (remove from user XDC)

**Rationale:**
- Clocking Wizard automatically creates `create_clock` for input port
- Having both IP and user XDC define the same clock causes conflicts
- Xilinx best practice: let IP cores own their clock constraints
- Eliminates timing warnings about "clock not reached"

**Alternatives Considered:**
- **User XDC owns all clocks:** More explicit control but requires disabling IP auto-constraints
- **Both define clocks:** Causes Vivado warnings and timing analysis confusion

**Trade-offs:**
- ✅ Clean timing reports (no constraint conflicts)
- ✅ Follows Xilinx recommended flow
- ⚠️ Less explicit control in XDC file
- ⚠️ Must understand IP's auto-generated constraints

---

## 8. Hardware Stimulus: BRAM-Based Generator

**Decision:** Use BRAM-based stimulus generator for hardware testing (not tie to zero)

**Rationale:**
- Tying inputs to zero would process silence and give no useful output
- Need to verify UART, LEDs, and state machine work on actual hardware
- BRAM stimulus uses same `.hex` files as simulation, ensuring consistency
- Temporary solution until real ADC is connected

**Alternatives Considered:**
- **Tie to zero:** Saves BRAM but can't verify functionality
- **External signal generator:** More realistic but requires additional hardware
- **AXI-based data injection:** More flexible but complex to implement

**Trade-offs:**
- ✅ Enables full hardware verification
- ✅ Uses same test data as simulation
- ⚠️ Uses ~2 BRAM36s for stimulus storage
- ⚠️ Not a real-world scenario (static signal, no noise/dynamics)

---

## 9. Acquisition Block Size: 1ms (Not Continuous)

**Decision:** Process data in 1ms blocks (4096 samples) for acquisition

**Rationale:**
- GPS C/A code repeats every 1ms (1023 chips at 1.023 MHz)
- FFT-based correlation works on fixed-size blocks
- Continuous processing is handled by Tracking Channel (next phase)
- Matches industry standard (greta-oto, gnss-sdr, commercial receivers)

**Alternatives Considered:**
- **Continuous streaming:** Would require different algorithm (not FFT-based)
- **2ms blocks:** Would capture 2 code periods but complicate correlation
- **Variable block size:** More flexible but harder to implement

**Trade-offs:**
- ✅ Matches GPS signal structure
- ✅ Enables efficient FFT-based correlation
- ⚠️ Requires buffering 4096 samples before processing
- ⚠️ Cannot track Doppler/code changes within the 1ms block

---

## 10. Two-Stage Doppler Search: Coarse (1000 Hz) + Fine (50 Hz)

**Decision:** Use two-stage search: 11 coarse bins (1000 Hz step) then 21 fine bins (50 Hz step)

**Rationale:**
- Coarse search quickly narrows Doppler to ±500 Hz
- Fine search refines to ±500 Hz with 50 Hz resolution
- Total search: 11 + 21 = 32 bins (vs 101 bins for single-stage 100 Hz search)
- Reduces acquisition time by ~3×

**Alternatives Considered:**
- **Single-stage 100 Hz search:** Simpler but 3× slower
- **Three-stage search:** Even faster but adds complexity
- **FFT-based Doppler search:** More efficient but requires larger FFT

**Trade-offs:**
- ✅ Fast acquisition (32 bins vs 101)
- ✅ Good Doppler resolution (50 Hz final)
- ⚠️ More complex state machine
- ⚠️ Requires storing coarse best for fine search centering

---

## 11. Parabolic Interpolation: Sub-Chip Code Phase

**Decision:** Use parabolic interpolation on 3 adjacent bins to estimate fractional code phase

**Rationale:**
- FFT gives integer bin index (1 chip resolution)
- True peak may be between bins
- Parabolic fit to bins k-1, k, k+1 gives fractional offset (1/256 chip resolution)
- Improves code phase accuracy without increasing FFT size

**Alternatives Considered:**
- **No interpolation:** Simpler but only 1 chip resolution
- **Zero-padding FFT:** Better resolution but increases FFT size and BRAM
- **Quadratic interpolation:** Same as parabolic, just different name

**Trade-offs:**
- ✅ Sub-chip resolution (1/256 chip)
- ✅ No additional BRAM or FFT size increase
- ⚠️ Adds 3 clock cycles of latency
- ⚠️ Requires edge-case handling (wrap-around at bin 0 and 4095)

---

## 12. Non-Coherent Integration (NCI): Magnitude Squared Accumulation

**Decision:** Use non-coherent integration (sum of magnitude squared) instead of coherent

**Rationale:**
- GPS navigation data bits flip every 20ms (50 bps)
- Coherent integration would cancel out if bit flip occurs mid-integration
- NCI (squaring magnitude) removes phase, making it immune to bit flips
- Provides ~10 dB sensitivity gain (with 10 frames)

**Alternatives Considered:**
- **Coherent integration:** Better SNR but fails with data bit transitions
- **Differential correlation:** Immune to bit flips but more complex
- **Bit synchronization first:** Would allow coherent 20ms, but requires tracking first

**Trade-offs:**
- ✅ Immune to navigation data bit flips
- ✅ Significant sensitivity gain (~10 dB)
- ⚠️ 3 dB loss compared to coherent integration
- ⚠️ Requires magnitude squared computation (adds DSP usage)

---

## 13. FFT-Based Parallel Correlation

**Decision:** Use FFT to correlate against all code phases simultaneously

**Rationale:**
- Serial correlator: test 4096 code phases one-by-one (4096 iterations)
- FFT correlator: FFT(signal) × FFT(code)* → IFFT = all 4096 correlations at once
- Massive speedup: ~4096× faster than serial
- Industry standard for GNSS acquisition

**Alternatives Considered:**
- **Serial correlator:** Simpler but 4096× slower
- **Matched filter:** Real-time but uses massive amount of DSP
- **Hybrid approach:** FFT for coarse, serial for fine - adds complexity

**Trade-offs:**
- ✅ Extremely fast (all code phases in parallel)
- ✅ Efficient use of FFT IP
- ⚠️ Requires storing code FFT in ROM (uses BRAM)
- ⚠️ Must buffer entire 1ms block before processing

---

## 14. Hardware Verification Strategy: Python Golden Model

**Decision:** Create Python script to cross-verify FPGA results against mathematical model

**Rationale:**
- Simulation can pass but still have mathematical errors
- Python provides independent verification using floating-point math
- Catches scaling issues, sign errors, and algorithmic bugs
- Industry best practice for FPGA verification

**Alternatives Considered:**
- **Simulation only:** Can miss subtle math errors
- **Hardware-only testing:** Expensive and slow to debug
- **Formal verification:** Overkill for this application

**Trade-offs:**
- ✅ High confidence in correctness
- ✅ Catches bugs before hardware deployment
- ⚠️ Requires maintaining two codebases (Verilog + Python)
- ⚠️ Python uses floating-point, FPGA uses fixed-point (expect magnitude differences)

## Conclusion

These decisions represent a balanced approach to GNSS acquisition engine design, prioritizing:
1. **Fit within target hardware** (Zynq-7020 resource constraints)
2. **Verification confidence** (Python cross-check, simulation)
3. **Industry best practices** (FFT correlation, NCI, two-stage search)
4. **Future extensibility** (clean architecture for tracking channel addition)

The design successfully demonstrates a production-grade acquisition engine while leaving room for future enhancements (tracking channel, real ADC integration, AXI interface).

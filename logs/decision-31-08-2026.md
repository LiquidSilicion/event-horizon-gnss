## 1. Executive Summary

Today we finalized the architecture for the FFT-based acquisition engine after a comprehensive study of three key research papers (Majoral 2023, Leclère 2015, Guruprasad 2015) and two reference implementations (`gnss-sdr` and `greta-oto`). This document captures every architectural decision made, the rationale behind it, and the research/evidence supporting it.

## 2. Architecture-Level Decisions

### Decision 2.1: Hybrid Acquisition Architecture
**Decision:** Combine FFT-based Parallel Code Phase Search (PCPS) from `gnss-sdr` with time-domain matched filter concepts from `greta-oto`.

**Rationale:**
- FFT-based PCPS finds all 4096 code phases simultaneously in the frequency domain — mathematically elegant and proven in production SDR receivers.
- Time-domain matched filters (greta-oto) are resource-efficient and map beautifully to FPGA fabric.
- The hybrid approach gives us the best of both worlds: low latency, deterministic behavior, and excellent resource utilization on the Zynq-7020.

**Reference:** Majoral et al. (Sensors 2023) validates this exact hybrid SoC-FPGA partitioning approach.

---

### Decision 2.2: Sampling Rate — 4 MHz (with 16 MHz upgrade path)
**Decision:** Use 4 MHz sampling rate (4000 samples/ms) for the initial acquisition engine, with a documented upgrade path to 16 MHz.

**Rationale:**
- **Matches existing tracking engine** — no resampler needed, eliminating a major source of complexity and potential bugs.
- **Fits comfortably in Zynq-7020** — a 4096-point FFT uses only ~16 BRAMs and ~15 DSPs, leaving >80% of the FPGA fabric free for 12+ tracking channels.
- **Code phase resolution is acceptable** — 0.256 chips/sample ≈ 244 meters, which is well within the pull-in range of a standard DLL with ±0.5 chip early/late spacing.
- **Upgrade path is clean** — when we need better resolution (e.g., for Galileo E1 BOC(1,1) or GPS L5), we can move to 16 MHz and apply Leclère's FFT splitting without redesigning the entire architecture.

---

### Decision 2.3: SoC Partitioning (FPGA vs ARM)
**Decision:** Heavy DSP in FPGA (acquisition, tracking multicorrelators), ARM PS handles loop filters, navigation message decoding, and PVT computation.

**Rationale:**
- Based on Majoral et al. 2023: FPGA handles sample-rate processing (computationally expensive, parallelizable), ARM handles floating-point navigation and control logic (flexible, sequential).
- This partitioning yields ~5-15W power consumption on Zynq platforms, vs 28W for a pure PC-based GNSS-SDR receiver.
- AXI4-Lite interface between PS and PL is the industry standard for this type of SoC design.

## 3. Signal Processing Decisions

### Decision 3.1: FFT Size — 4096 points
**Decision:** Zero-pad 4000 samples to 4096 points (next power of 2).

**Rationale:**
- Xilinx FFT IP core requires power-of-2 transform lengths for optimal efficiency.
- Only 96 samples of zero-padding needed — minimal spectral leakage.
- 4096-point FFT provides 4096 code phase bins, giving ~0.256 chips/bin resolution.

---

### Decision 3.2: FFT IP Core Configuration
**Decision:** Xilinx FFT IP, Radix-4 Burst I/O architecture, Block Floating Point scaling.

**Rationale:**
- **Radix-4 Burst I/O** uses ~40% less BRAM than Pipelined Streaming architecture while maintaining high throughput (per Guruprasad 2015 Table 5).
- **Block Floating Point scaling** is critical — it dynamically scales the output to prevent overflow without losing weak signals. This directly addresses the accuracy pitfalls documented in Guruprasad's thesis where fixed scaling destroyed acquisition sensitivity.

---

### Decision 3.3: FFT Splitting — NOT needed for 4 MHz
**Decision:** Do not implement Leclère's FFT splitting (9-FFT or 15-FFT) for the current 4 MHz design, but architect the system to support it for future expansion.

**Rationale:**
- FFT splitting is only beneficial for FFT sizes ≥ 16384 points.
- At 4096 points, splitting adds unnecessary complexity with no resource benefit.
- **Future trigger:** When we upgrade to 16 MHz (16384-point FFT) or implement 4 ms coherent integration (65536-point FFT), FFT splitting becomes critical:
  - 9-FFT solution: 73.5% BRAM reduction vs standard 3-FFT
  - 15-FFT solution: 84.3% BRAM reduction vs standard 3-FFT

**Reference:** Leclère et al. 2015, Table 3.

---

### Decision 3.4: Complex Multiplier — 3-Multiplier Gauss Optimization
**Decision:** Use the 3-multiplier optimization instead of the standard 4-multiplier approach.

**Rationale:**
- Saves 25% of DSP48 slices (3 multipliers instead of 4).
- Critical for Zynq-7020 which only has 220 DSP48E1 slices.
- The slight increase in adder usage is negligible since adders are cheap in LUTs.

---

### Decision 3.5: Butterfly Arithmetic — XtremeDSP Slices
**Decision:** Use DSP48 built-in adders for butterfly operations instead of LUT-based adders.

**Rationale:**
- DSP48E1 has dedicated 48-bit adder/subtractor hardware.
- More efficient than LUT-based implementation, faster timing closure.
- Frees up LUTs for other logic.

---

### Decision 3.6: Peak Detector — Safe Bit-Slicing
**Decision:** Compute I² + Q² using explicit bit-slicing `[47:16]` instead of the `>>> 16` shift operator.

**Rationale:**
- The `>>>` operator can cause Vivado synthesis warnings about signed/unsigned truncation.
- Explicit bit-slicing is the industry-standard way to implement a logical right shift in RTL.
- Guarantees a clean 32-bit positive magnitude output with no sign-extension surprises.

## 4. FPGA Resource Decisions

### Decision 4.1: Bit Width — 18-bit Signed Data Path
**Decision:** Use 18-bit signed data throughout the acquisition engine (matching DSP48E1 native multiplier width).

**Rationale:**
- **Directly addresses Guruprasad 2015 findings:** 8-bit FFT data paths caused severe accuracy loss — satellites were missed or falsely acquired due to truncation.
- 18-bit maps perfectly to Xilinx DSP48E1 multipliers (25×18 bit architecture), giving maximum accuracy with zero wasted logic.
- Provides 108 dB dynamic range — more than sufficient for GNSS signals.

---

### Decision 4.2: PRN FFT ROM — Pre-computed in BRAM
**Decision:** Pre-compute the complex-conjugated FFT of all 32 GPS PRN codes in Python, store in BRAM using the `(* ram_style = "block" *)` synthesis attribute.

**Rationale:**
- Pre-computation saves massive real-time computation — the conjugated FFT is reused for every Doppler bin search.
- The `(* ram_style = "block" *)` attribute forces Vivado to infer dedicated Block RAM instead of wasting thousands of LUTs on distributed RAM.
- 32 PRNs × 4096 bins × 36 bits (18-bit I + 18-bit Q) = ~5.9 Mb ≈ 16 BRAMs.

---

### Decision 4.3: Clock Domain Crossing — 100 MHz → 200 MHz
**Decision:** Use MMCM/PLL to generate a 200 MHz clock, with an Async FIFO (AXI4-Stream) to bridge the 100 MHz sample collection domain to the 200 MHz FFT processing domain.

**Rationale:**
- Doubles FFT throughput, cutting FFT latency in half.
- Async FIFO handles the clock domain crossing safely with proper synchronization.
- Minimal resource cost (one MMCM + one FIFO) for a 2× performance gain.

---

### Decision 4.4: State Machine — Sequential with Intermediate BRAM Buffers
**Decision:** Use a sequential state machine with intermediate BRAM buffers (`i_buffer`, `q_buffer`, `fft_i_mem`, `mult_i_mem`) instead of complex streaming handshakes.

**Rationale:**
- Prevents handshaking deadlocks with the Xilinx FFT IP.
- Clean, predictable data flow: `BRAM → FFT → BRAM → Multiplier → BRAM → IFFT → Peak Detect`.
- Easier to debug and verify in simulation.
- Time-multiplexes a single FFT IP core for both Forward FFT and IFFT, saving resources.

## 5. Implementation & Synthesis Decisions

### Decision 5.1: NCO ROM for Carrier Wipe-off
**Decision:** 4096-entry sine/cosine lookup table, 18-bit signed, generated via Python script.

**Rationale:**
- Efficient carrier wipe-off without the complexity of a CORDIC algorithm.
- 4096 entries provide fine phase resolution (360°/4096 ≈ 0.088° per bin).
- Matches the 18-bit data path of the rest of the engine.

---

### Decision 5.2: Master Combined Hex Files
**Decision:** Use master combined hex files (`all_prns_fft_i.hex`, `all_prns_fft_q.hex`) instead of 64 separate per-PRN files.

**Rationale:**
- Verilog `$readmemh` does not support `$sformatf` for dynamic filenames in standard Verilog-2001.
- Combined files are cleaner, faster to load during simulation elaboration.
- Matches the existing `ca_code_all_prns.hex` workflow established during the tracking engine development.

---

### Decision 5.3: Python Golden Model
**Decision:** Build a Python simulation (`gnss_acquisition.py`) that mirrors the FPGA fixed-point behavior before writing RTL.

**Rationale:**
- Provides a "golden reference" to compare against the Verilog simulation.
- Validates the PCPS algorithm mathematically before committing to hardware.
- Generates the ROM initialization files (`.hex`) needed for BRAM loading.
- Allows rapid iteration on algorithm parameters (Doppler search grid, threshold, etc.).

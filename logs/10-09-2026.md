### 2. Sampling Rate Clarification & 4 MHz Implementation

**Discussion Points:**
- User questioned whether acquisition should process continuous data vs. 1ms blocks
- Clarified that acquisition correctly uses 1ms FFT blocks (4096 samples at 4 MHz)
- Continuous processing happens in the **Tracking Channel** (next phase), not acquisition
- Referenced `greta-oto` project architecture confirming industry-standard approach

**Decision:** Use **4 MHz sampling rate** (100 MHz / 25 = 4 MHz) for hardware implementation
- Achieved via clock divider counter in `acquisition_top.v`
- 4096 samples at 4 MHz = 1.024 ms (acceptable for acquisition)
- Alternative would be 4.096 MHz, but 4 MHz is cleaner integer division

**Implementation:**
```verilog
reg [4:0] sample_div_counter;
wire sample_en;

always @(posedge clk_100) begin
    if (sample_div_counter == 5'd24)
        sample_div_counter <= 5'd0;
    else
        sample_div_counter <= sample_div_counter + 1'b1;
end

assign sample_en = (sample_div_counter == 5'd24);  // 4 MHz pulse
```

### 4. BRAM Overutilization Resolution

**Problem:** Initial synthesis reported 339 BRAM18s used, exceeding Zynq-7020's 280 BRAM18 limit

**Root Cause Analysis:**
- `code_fft_rom` storing 32 PRNs × 4096 samples × 36 bits (I+Q) = ~128 BRAM36s
- FFT IP core internal buffers = ~12 BRAM36s
- FIFOs and NCI accumulator = ~8 BRAM36s
- **Total: ~148 BRAM36s (296 BRAM18s)** ❌

**Solution Implemented:**
1. **Reduced PRNs from 32 to 16** in `code_fft_rom.v`
   - Changed array size from `[0:32*FFT_SIZE-1]` to `[0:16*FFT_SIZE-1]`
   - Updated `doppler_search_controller.v` to search PRNs 1-16 (1-based indexing)
   - Saves ~64 BRAM36s

2. **Reduced NCI_FRAMES from 20 to 10** in `acquisition_engine` instantiation
   - Reduces NCI accumulator depth
   - Saves ~4 BRAM36s

**Final Resource Utilization:**
```
BRAM36:  ~86 / 140  (61% utilization) ✅
DSP48:   ~16 / 220  (7% utilization) ✅
LUTs:    ~12,714 / 53,200  (24% utilization) ✅
```

**Result:** Design now fits comfortably within Zynq-7020 resources with 39% BRAM headroom for future expansion.

### 5. Clock Constraint & Timing Issue Resolution

**Problem:** Vivado reported critical timing warnings:
```
[Constraints 18-1056] Clock 'sys_clk_pin' completely overrides clock 'clk_100'
TIMING #1 Critical Warning The clock pin ... is not reached by a timing clock
44,500 failing endpoints
```

**Root Cause:**
- User's XDC file defined `create_clock -name sys_clk_pin` on `clk_100` port
- Clocking Wizard IP auto-generated `create_clock` on same port with name `clk_100`
- Two conflicting clock definitions caused timing analyzer confusion

**Solution:**
- Removed `create_clock` line from user's XDC file
- Let Clocking Wizard IP be the single source of truth for input clock definition
- IP automatically creates `clk_100` primary clock and `clk_out1_clk_wiz_200mhz` generated clock

**Result:** All timing warnings resolved, proper clock hierarchy established:
```
clk_100 (100 MHz, primary) ← Auto-generated by Clocking Wizard IP
   └── clk_out1_clk_wiz_200mhz (200 MHz, generated)
```

## 🔧 Technical Decisions & Trade-offs

| Decision | Rationale | Trade-off |
|:---|:---|:---|
| **4 MHz sampling rate** | Clean integer division from 100 MHz | 1.024 ms per FFT (vs. 1.000 ms at 4.096 MHz) |
| **16 PRNs instead of 32** | Fits within Zynq-7020 BRAM limits | Can only search half the GPS constellation |
| **10 NCI frames instead of 20** | Reduces BRAM usage | Lower sensitivity gain (~10 dB vs. ~13 dB) |
| **1-based PRN indexing** | Matches GPS PRN numbering (1-32) | Requires offset logic in controller |
| **Clocking Wizard owns clock definition** | Eliminates constraint conflicts | Less explicit control in XDC |

## 💡 Lessons Learned

1. **BRAM is the limiting resource** in FFT-based GNSS receivers - always budget for code FFT storage first
2. **Python cross-verification is essential** - caught potential issues before hardware deployment
3. **Clock constraint conflicts are common** - let IP cores own their clock definitions when possible
4. **1ms FFT blocks are correct** for acquisition - continuous processing belongs in tracking stage
5. **Sub-chip interpolation at boundaries** requires careful wrap-around logic (bin 0 ↔ bin 4095)

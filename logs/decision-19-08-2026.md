## 2. Timing Constraints & Clock Architecture

### 2.1 System Clock: 100 MHz

**Decision:** Operate the entire tracking datapath at 100 MHz (10 ns period).

**Rationale:**

1. **Timing Closure Margin:** 
   - Achieved WNS (Worst Negative Slack): **+1.823 ns** ✅
   - Critical path delay: **8.177 ns** (87.9% logic, 12.1% routing)
   - This provides an **18.2% timing margin** at the slow process corner, ensuring robust operation across temperature and voltage variations.

2. **Sample Rate Compatibility:**
   - Target sample rate: 4 MHz (4 MSPS)
   - At 100 MHz clock, we have **25 clock cycles per sample**
   - This provides ample time for:
     - Carrier NCO phase accumulation
     - Sine/cosine ROM lookup
     - Complex mixing (4 multiplications + 2 additions)
     - Code NCO update and C/A code generation
     - Correlation accumulation

3. **Framework Alignment:**
   > *"The process of designing for timing closure—using synthesis, placement, and routing tools to ensure that all combinational paths between registers meet the setup and hold time requirements for the target clock frequency—is central to achieving deterministic performance."*

4. **Multi-Corner Analysis:**
   - Verified at **Slow Corner** (max temperature, min voltage): WNS = +1.823 ns
   - Verified at **Fast Corner** (min temperature, max voltage): WHS = +0.119 ns
   - All timing constraints met across both corners ✅

### 2.2 Hold Time Constraints

**Decision:** Ensure positive hold slack across all paths.

**Result:**
- Worst Hold Slack (WHS): **+0.119 ns** ✅
- Total Hold Endpoints: 38
- Hold Violations: **0**

**Rationale:**
Hold time violations cannot be fixed by slowing the clock—they indicate a fundamental design flaw. The positive hold slack confirms that data arrives at destination registers sufficiently after the clock edge, preventing race conditions.

## 3. Bit-Width & Precision Decisions

### 3.1 Carrier Phase NCO: 48-Bit Accumulator

**Decision:** Use a 48-bit phase accumulator for the carrier NCO.

**Rationale:**

1. **Centimeter-Level Accuracy Requirement:**
   - GPS L1 wavelength (λ): **19.03 cm**
   - 48-bit resolution: $2^{-48}$ cycles = **3.55 × 10⁻¹⁵ cycles**
   - Distance resolution: 19.03 cm × 3.55 × 10⁻¹ = **6.76 × 10⁻¹⁴ cm**
   - This provides **14 orders of magnitude** beyond the 1 cm RTK requirement.

2. **Dynamic Platform Considerations:**
   > *"For dynamic platforms like drones or autonomous vehicles, update rates and latency are as crucial as static positional accuracy."*
   
   While 32 bits would suffice for static accuracy (4.4 × 10⁻⁹ cm), the 48-bit width prevents **phase truncation error accumulation** over long tracking periods in high-dynamics scenarios (UAVs at 200 Hz update rates).

3. **Resource Trade-off:**
   - 48-bit adder: ~48 LUTs (negligible on Zynq-7020 with 53,200 LUTs)
   - Justified by the framework principle: *"Managing Precision and Performance Trade-offs via Algorithmic and Numerical Optimization"*

### 3.2 Code Phase NCO: 32-Bit Accumulator

**Decision:** Use a 32-bit phase accumulator for the code NCO.

**Rationale:**

1. **Precision Analysis:**
   - C/A code chip length: **293.05 m**
   - 32-bit resolution: $2^{-32}$ chips = **2.33 × 10⁻¹⁰ chips**
   - Distance resolution: 293.05 m × 2.33 × 10⁻¹⁰ = **68.2 nm**
   - This provides **7 orders of magnitude** beyond the 1 m pseudorange requirement.

2. **Resource Optimization:**
   > *"Fixed-point representation, which uses integers to represent fractional numbers, is far more hardware-efficient."*
   
   Increasing to 48 bits would waste DSP/BRAM resources without improving RTK fix quality, as code multipath noise dominates at the centimeter level anyway.

### 3.3 Correlator Accumulators: 32-Bit Signed

**Decision:** Use 32-bit signed accumulators for the Integrate-and-Dump (I&D) correlators.

**Rationale:**

1. **Overflow Prevention:**
   - Max input amplitude: 2¹⁵ - 1 = **32,767** (16-bit signed sample)
   - Samples per epoch: **4,000** (at 4 MHz sample rate × 1 ms)
   - Max theoretical accumulation: 32,767 × 4,000 = **1.31 × 10⁸**
   - 32-bit signed max: 2³¹ - 1 = **2.15 × 10⁹**
   - **Headroom:** 16.4× safety margin

2. **Framework Alignment:**
   > *"Studies have shown that quantizing the weights and activations of machine learning models to 8-bit integers can drastically reduce resource consumption while preserving acceptable accuracy."*
   
   Applied to GNSS: 32-bit accumulators provide sufficient dynamic range while minimizing LUT/DSP usage.

### 3.4 Sample Width: 16-Bit Signed I/Q

**Decision:** Process 16-bit signed I/Q samples from the RF front-end.

**Rationale:**

1. **ADC Compatibility:**
   - Standard RF ADCs (e.g., AD9361) provide 12-14 bit resolution
   - 16-bit processing preserves ADC dynamic range with 2-4 bits of headroom

2. **DSP Mapping:**
   - Xilinx DSP48E1 slices have 25×18-bit inputs
   - 16-bit samples map natively, enabling **II=1 pipelined correlation** without extra LUTs for bit-width adaptation

3. **Resource Efficiency:**
   - 16-bit × 16-bit multiplication: 1 DSP48 slice
   - 18-bit × 18-bit multiplication: 1 DSP48 slice (no difference)
   - Using full 18 bits would waste precision without performance gain

## 4. Architectural Decisions

### 4.1 Scalar Tracking Baseline

**Decision:** Implement a scalar tracking engine as the Phase 1 baseline before advancing to vector tracking.

**Rationale:**

1. **Modularity Principle:**
   > *"Modularity, the practice of dividing the system into discrete, interchangeable components, is essential for managing complexity and facilitating development and verification."*
   
   Scalar tracking channels are independent, self-contained modules that can be:
   - Developed and verified independently
   - Replicated for multi-channel operation
   - Later integrated into a vector tracking architecture

2. **WCET-Centric Design:**
   > *"The only way to ensure that a complex, concurrent system meets these hard real-time constraints is through rigorous Worst-Case Execution Time (WCET) analysis."*
   
   Scalar channels have **deterministic, independent timing**:
   - Each channel processes samples in parallel
   - No inter-channel dependencies
   - WCET is bounded by the 1 ms integration period

3. **Foundation for Vector Tracking:**
   The scalar baseline provides:
   - Verified correlator datapath
   - Characterized timing performance
   - Known resource utilization
   - Interface for future EKF steering

### 4.2 Fully Pipelined Datapath (II=1)

**Decision:** Design all datapaths with an Initiation Interval (II) of 1 clock cycle.

**Rationale:**

1. **Throughput Maximization:**
   > *"Best practice dictates that designs should be fully pipelined, aiming for an initiation interval (II) of 1 clock cycle, meaning a new input is accepted every clock cycle."*
   
   - At 100 MHz with II=1: **100 million samples/second** throughput
   - Required sample rate: 4 MHz
   - **25× headroom** for future higher-rate operation

2. **Pipeline Stages:**
   The critical path analysis reveals the pipeline structure:
   - 7 logic levels
   - Each stage registered
   - No combinational bubbles

3. **Resource Utilization:**
   - Total LUTs: **134** (0.25% of 53,200)
   - Total FFs: **193** (0.18% of 106,400)
   - DSP48s: **2** (0.91% of 220)
   - BRAMs: **5** (3.57% of 140)
   
   > *"The extremely low cost of pipelining registers in modern FPGAs enables designers to break down complex computations into fine-grained stages."*

### 4.3 Heterogeneous SoC Architecture (Zynq-7020)

**Decision:** Target the Xilinx Zynq-7020 SoC (ARM Cortex-A9 + FPGA fabric).

**Rationale:**

1. **Hardware/Software Co-Design:**
   > *"The proposed framework should leverage a heterogeneous System-on-Chip (SoC) platform, such as a Xilinx Zynq UltraScale+ MPSoC, which combines a hard processor system (like an ARM Cortex-A) with programmable logic."*
   
   **FPGA Fabric (PL):**
   - Carrier/code NCOs
   - Mixers and correlators
   - Integrate-and-Dump accumulators
   - **Deterministic, cycle-accurate processing**
   
   **ARM Processor (PS):**
   - Loop filter calculations (PLL/DLL)
   - Navigation message decoding
   - PVT solution
   - **Flexible control and sequencing**

2. **Scalability:**
   > *"Scalability ensures the system can adapt to changing requirements or advancements in technology without a complete redesign."*
   
   Current utilization leaves massive headroom:
   - **Single channel:** 2 DSP48s, 5 BRAMs
   - **Zynq-7020 capacity:** 220 DSP48s, 140 BRAMs
   - **Theoretical max channels:** 110 (DSP-limited) or 28 (BRAM-limited)
   - **Realistic target:** 20-24 channels (leaves room for KF accelerator)

3. **WCET Analysis:**
   - **FPGA:** Cycle-accurate, 0 ns jitter
   - **ARM:** RTOS-scheduled tasks with bounded WCET
   - **Combined:** End-to-end latency guarantee

### 4.4 1 ms Integration Epoch

**Decision:** Use a 1 ms coherent integration period.

**Rationale:**

1. **C/A Code Period:**
   - GPS L1 C/A code repeats every **1 ms** (1023 chips at 1.023 MHz)
   - Coherent integration must align with code period to avoid data bit transitions

2. **Real-Time Deadline:**
   > *"For dynamic platforms like drones or autonomous vehicles, update rates and latency are as crucial as static positional accuracy."*
   
   - 1 ms epoch → **1 kHz update rate**
   - Standard surveying: 1 Hz
   - UAV photogrammetry: 5-10 Hz
   - Mobile mapping: up to 200 Hz
   - **Our design:** 1000 Hz (10× beyond mobile mapping requirements)

3. **ARM Processing Budget:**
   - FPGA integration: 1.000 ms (fixed)
   - ARM read/write overhead: ~13 µs
   - Loop filter computation: ~10 µs
   - **Total:** ~23 µs ARM overhead
   - **Slack:** 977 µs (97.7% margin)
   
   This massive margin allows the ARM to:
   - Run an RTOS scheduler
   - Handle multiple channels
   - Execute navigation decoding
   - All while meeting the 1 ms deadline

## 5. Verification & Validation Decisions

### 5.1 Self-Contained Testbench

**Decision:** Replace file-based I/O with internal stimulus generation.

**Rationale:**

1. **Determinism:**
   > *"The FPGA itself provides a uniquely suitable substrate for building systems amenable to WCET analysis due to its inherent parallelism and deterministic nature."*
   
   File I/O introduces:
   - Non-deterministic latency
   - Endianness bugs
   - Path resolution errors
   
   Internal stimulus provides:
   - Cycle-accurate timing
   - Reproducible results
   - No external dependencies

2. **Verification Result:**
   - I_P output: **5,190,080** (stable across 10 epochs)
   - Q_P output: **~0** (carrier locked)
   - **Zero jitter** in dump_valid timing

### 5.2 Multi-Corner Timing Analysis

**Decision:** Verify timing at both Slow and Fast process corners.

**Rationale:**

1. **Process Variation:**
   > *"This is critical because smaller semiconductor geometries make interconnect delays dominant and highly variable, making single-model timing analysis insufficient."*
   
   - **Slow Corner:** Max temperature (85°C), min voltage (0.95V)
   - **Fast Corner:** Min temperature (0°C), max voltage (1.05V)
   - Ensures operation across all environmental conditions

2. **Result:**
   - Slow corner WNS: **+1.823 ns** ✅
   - Fast corner WHS: **+0.119 ns** ✅
   - **All constraints met** across both corners

### 5.3 Software Loop Filter Simulation

**Decision:** Validate the ARM-side loop filter in software before hardware integration.

**Rationale:**

1. **Algorithm Verification:**
   > *"The Kalman filter is a widely adopted algorithm for real-time state estimation and has been extensively implemented in hardware on FPGAs."*
   
   Before committing to hardware:
   - Verify discrete-time coefficient calculation
   - Confirm convergence behavior
   - Characterize lock time and steady-state error

2. **Result:**
   - Initial frequency error: **5.0 Hz**
   - Final frequency error: **0.000112 Hz**
   - Convergence time: **~300 ms**
   - **PLL locked** with sub-milliHertz accuracy

## 6. Resource Utilization & Scalability

### 6.1 Current Utilization (Single Channel)

| Resource | Used | Available | % Used | Justification |
|----------|------|-----------|--------|---------------|
| **LUT** | 134 | 53,200 | 0.25% | Minimal logic for NCOs, control |
| **FF** | 193 | 106,400 | 0.18% | Pipeline registers for II=1 |
| **DSP48** | 2 | 220 | 0.91% | 1 mixer + 1 MAC (expandable) |
| **BRAM** | 5 | 140 | 3.57% | Sincos ROM + 3× C/A code ROMs |

### 6.2 Multi-Channel Scaling Projection

**Decision:** Design for 20-24 simultaneous tracking channels.

**Rationale:**

1. **Resource Budget:**
   - 24 channels × 2 DSP48s = **48 DSP48s** (21.8% of 220)
   - 24 channels × 5 BRAMs = **120 BRAMs** (85.7% of 140)
   - 24 channels × 134 LUTs = **3,216 LUTs** (6.0% of 53,200)
   - **Leaves room for:** Kalman Filter accelerator, IMU interface, RTK engine

2. **GPS + GLONASS + Galileo:**
   - GPS L1: 12 satellites
   - GLONASS L1: 12 satellites
   - Galileo E1: 12 satellites
   - **Total:** 36 channels (requires BRAM optimization or external memory)

3. **Framework Alignment:**
   > *"Scalability ensures the system can adapt to changing requirements or advancements in technology without a complete redesign."*

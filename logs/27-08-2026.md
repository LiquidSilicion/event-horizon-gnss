## 2. Key Challenges & Resolutions

### 2.1 The "Silent ROM" Bug (C/A Code Not Loading)

**Symptom:** Simulation outputs showed `I_P = x` or `0`, and the correlator failed to accumulate any meaningful signal.

**Root Cause:** The `$readmemh` function in `ca_code_gen.v` used a relative path (`"ca_code_all_prns.hex"`). The XSim simulator runs in a hidden `xsim` directory, causing it to silently fail and leave the Block RAM initialized to `x` or `0`.

**Resolution:** Updated `$readmemh` to use an absolute path:
```verilog
$readmemh("/home/johan2/Documents/fpga/event-horizon-gnss/data/rom_data/ca_code_all_prns.hex", code_rom);
```
Added a `$display` statement to explicitly confirm successful loading in the console.

### 2.2 The Reset Polarity Trap

**Symptom:** The design remained perpetually in reset during simulation and on hardware, despite the reset button being released.

**Root Cause:** The ZedBoard's BTNC button (Pin P16) is **Active-High** (pulls to VCC when pressed, `0` when released). The internal RTL logic was written for a standard **Active-Low** reset (`if (!rst_n)`). When the button was released (`0`), `!0` evaluated to `1`, holding the design in reset.

**Resolution:** Added an inversion wire at the top level of `tracking_top.v`:
```verilog
wire rst_internal = ~rst_n; // Converts Active-High pin to Active-Low internal signal
```
All internal modules were updated to use `rst_internal`.

### 2.3 The 10-Bit Collision Bug (Early == Late)

**Symptom:** In simulation, `I_E` was always exactly equal to `I_L`, and `Q_E` equaled `Q_L`, making Delay Lock Loop (DLL) tracking mathematically impossible.

**Root Cause:** The Early/Late chip indices were calculated using 10-bit unsigned arithmetic:
```verilog
wire [9:0] chip_idx_e = chip_idx_p - 10'd512;
wire [9:0] chip_idx_l = chip_idx_p + 10'd512;
```
In 10-bit math, `-512 ≡ +512 (mod 1024)`. Thus, Early and Late pointed to the exact same ROM address.

**Resolution:** Upgraded the calculation to 11-bit arithmetic with explicit modulo-1023 wrapping:
```verilog
wire [10:0] chip_idx_p_11 = {1'b0, chip_idx_p};
wire [10:0] chip_idx_e_11 = (chip_idx_p_11 >= 11'd512) ? 
                            (chip_idx_p_11 - 11'd512) : 
                            (chip_idx_p_11 + 11'd511);
wire [10:0] chip_idx_l_11 = (chip_idx_p_11 + 11'd512 >= 11'd1023) ? 
                            (chip_idx_p_11 + 11'd512 - 11'd1023) : 
                            (chip_idx_p_11 + 11'd512);
```

### 2.4 The Code NCO Wrap-Around Bug

**Symptom:** The C/A code sequence would garble or reset incorrectly after every 1 ms epoch.

**Root Cause:** In `code_nco.v`, the `chip_idx` was assigned the value of `code_phase` *before* the phase wrap-around logic was applied, due to Verilog's non-blocking assignment (`<=`) evaluation rules.

**Resolution:** Introduced a temporary combinational variable `next_phase` to compute the wrapped phase first, then assigned both `code_phase` and `chip_idx` from it:
```verilog
reg [PHASE_BITS-1:0] next_phase;
next_phase = code_phase + code_freq_word;
if (next_phase >= (CODE_LENGTH << (PHASE_BITS - CHIP_BITS)))
    next_phase = next_phase - (CODE_LENGTH << (PHASE_BITS - CHIP_BITS));
code_phase <= next_phase;
chip_idx   <= next_phase[PHASE_BITS-1 -: CHIP_BITS];
```

### 2.5 Frequency Word Mismatch in Testbench

**Symptom:** The carrier phase was not locking, and `Q_P` remained large.

**Root Cause:** The synthetic signal generator and the tracking channel were using mismatched frequency words for a 4 MHz sample rate.

**Resolution:** Recalculated and synchronized the frequency words:
- **Carrier (1 kHz Doppler @ 4 MHz):** `48'h000010624DD2F1`
- **Code (1.023 MHz @ 4 MHz):** `32'h4178D4FD`

## 3. Architectural Decisions & Configurations

| Component | Configuration | Rationale |
|-----------|---------------|-----------|
| **Sample Rate** | 4 MHz | Balances FPGA resource usage (DSP/BRAM) with sufficient oversampling for GPS L1 C/A (1.023 MHz). |
| **Accumulator Width** | 32-bit signed (Q16.16) | Prevents overflow during 4000-sample integration while retaining fractional precision for future loop filter operations. |
| **C/A Code Storage** | 1-bit per chip, 32 PRNs | Stored as a flat 32,736-entry ROM. Loaded via `$readmemh` with an absolute path for reliable simulation and synthesis. |
| **Reset Strategy** | Active-Low Internal | Standardizes reset logic across all sub-modules, with a single top-level inversion to match the ZedBoard's Active-High hardware button. |
| **Carrier NCO** | 48-bit phase accumulator | Provides sub-millimeter carrier phase resolution for future RTK positioning. |
| **Code NCO** | 32-bit phase accumulator | Provides fine code phase resolution with 10-bit chip index output. |

## 4. Acquisition Engine Architecture Study

### 4.1 FFT-Based PCPS (gnss-sdr Approach)

**Algorithm:** Parallel Code Phase Search using Fast Fourier Transform

**Core Principle:** Cross-Correlation Theorem: `x ⋆ y = ℱ⁻¹{ℱ{x} · ℱ{y}*}`

**Workflow:**
1. Pre-compute FFT of local C/A code (conjugated) and store in BRAM
2. For each Doppler hypothesis (e.g., ±10 kHz in 500 Hz steps):
   - Mix incoming signal with local carrier at hypothesized Doppler
   - Compute FFT of mixed signal
   - Multiply with pre-computed conjugated code FFT
   - Compute IFFT to get correlation for all 1023 code phases simultaneously
   - Compute magnitude squared: `P[k] = I² + Q²`
3. Find peak and compare to threshold (CFAR algorithm)

**Pros:**
- Computes all code phases in one FFT operation
- Highly efficient for software implementation
- Scales well to long codes (e.g., Galileo E1, GPS L5)

**Cons:**
- Requires large FFT IP cores (4096-16384 points)
- High BRAM usage for pre-computed code FFTs
- Complex control logic for Doppler search grid
- Higher latency due to FFT/IFFT operations

### 4.2 Time-Domain Matched Filter (greta-oto Approach)

**Algorithm:** Serial/Parallel correlation using shift registers and adder trees

**Core Principle:** Direct time-domain correlation: `P[τ] = Σ s[n] · c[n-τ]`

**Workflow:**
1. Shift incoming samples into a delay line (4000-16000 taps)
2. Generate local C/A code at specific code phase offset
3. Multiply each tap with corresponding code chip (XNOR for 1-bit, DSP for multi-bit)
4. Sum all products using pipelined adder tree
5. Coherent accumulation over N milliseconds
6. Non-coherent accumulation (magnitude squared) to mitigate data bit transitions
7. Peak detection and threshold comparison

**Pros:**
- Highly area-efficient
- Maps directly to FPGA LUTs and DSP slices
- Low latency (no FFT operations)
- Simple control logic
- Deterministic timing

**Cons:**
- Must iterate through code phases sequentially (unless parallelized)
- Higher DSP usage for multi-bit samples
- Scaling to multiple Doppler bins requires time-multiplexing or multiple correlators

### 4.3 Decision for Event Horizon Implementation

**Recommended Approach:** Hybrid strategy

**Initial Implementation:** Time-domain Matched Filter (greta-oto style)
- Lower resource utilization on Zynq-7020
- Faster time-to-first-fix for initial bring-up
- Easier to debug and verify in simulation
- Proven architecture from greta-oto reference design

**Future Optimization:** Consider FFT-based PCPS if supporting modern signals (Galileo E1, GPS L5) with longer codes (>10,000 chips)

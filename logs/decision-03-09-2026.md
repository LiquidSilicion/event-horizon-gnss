## 1. Doppler Frequency Correction

### Decision: Correct NCO Word from ~50 kHz to 1 kHz

**Initial Problem:**
The testbench was using `EXP_DOPPLER_WORD = 48'h000010624DD2F1`, which calculated to ~50 kHz Doppler - far outside the valid GPS L1 range (±5 kHz typical, ±10 kHz max).

**Mathematical Correction:**
```verilog
// Formula: carrier_freq_word = (f_doppler / f_clk) × 2^48
// For 1 kHz @ 200 MHz:
carrier_freq_word = (1000 / 200,000,000) × 281,474,976,710,656
                  = 1,407,374,883,553
                  = 48'h00000053E2D623
```

**Rationale:**
- GPS L1 Doppler range: ±5 kHz (stationary), ±10 kHz (high dynamics)
- 50 kHz is physically impossible for GPS signals
- Correcting to 1 kHz aligns with realistic GPS scenarios
- Enables proper validation of the acquisition pipeline

**Result:**
- Peak magnitude increased from 511,967 to 1,007,496 (97% improvement)
- Confirmed stimulus signal has ~0 Hz Doppler embedded
- Pipeline validated with correct Doppler parameters

**Trade-offs:**
- ✅ **Pro:** Physically realistic test scenario
- ✅ **Pro:** Revealed true signal characteristics (0 Hz Doppler)
- ❌ **Con:** Required re-validation of entire pipeline
- ❌ **Con:** Initial debugging time lost to incorrect parameter

## 2. 2D Search Architecture Decision

### Decision: Implement Testbench-Driven 2D Search First

**Approach:**
Implement Doppler iteration logic in the testbench (`tb_acquisition_engine.v`) rather than in RTL, using a `for` loop to iterate through 11 Doppler bins.

**Implementation:**
```verilog
// Testbench 2D search loop
for (doppler_bin = 0; doppler_bin < NUM_DOPPLER_BINS; doppler_bin = doppler_bin + 1) begin
    // Calculate NCO word for current bin
    doppler_hz = (doppler_bin - (NUM_DOPPLER_BINS/2)) * DOPPLER_STEP_HZ;
    current_doppler_word = calculate_nco_word(doppler_hz);
    
    // Feed data, start acquisition, wait for done
    feed_data_to_fifo();
    pulse_start();
    wait_for_done();
    
    // Track global best peak
    if (peak_magnitude > global_best_mag) begin
        global_best_mag = peak_magnitude;
        best_doppler_bin = doppler_bin;
    end
    
    // Reset DUT for next bin
    reset_dut();
end
```

**Rationale:**
- **Validation First:** Prove the acquisition engine works correctly before adding RTL complexity
- **Easier Debugging:** Testbench can print detailed logs, add breakpoints, inspect waveforms
- **Rapid Iteration:** Change search parameters (bins, step size) without re-synthesizing RTL
- **Incremental Development:** Get single-Doppler working first, then add 2D search

**Trade-offs:**
- ✅ **Pro:** Fast iteration cycle (no RTL changes needed)
- ✅ **Pro:** Comprehensive debug visibility
- ✅ **Pro:** Flexible parameter adjustment
- ❌ **Con:** Not synthesizable (testbench-only solution)
- ❌ **Con:** Requires external controller for real hardware deployment
- ❌ **Con:** Reset between bins adds overhead (~10 µs per bin)

**Performance:**
- 11 bins × ~150 µs/bin = ~1.65 ms total acquisition time
- Each bin requires full DUT reset and FIFO refill
- Acceptable for validation, not optimal for production

## 3. Hardware vs Testbench Implementation

### Decision: Create Dedicated RTL Doppler Search Controller

**Evolution:**
After validating with testbench-driven search, decided to create a hardware `doppler_search_controller.v` module for autonomous operation.

**Architecture:**
```verilog
module doppler_search_controller #(
    parameter NUM_DOPPLER_BINS = 11,
    parameter DOPPLER_STEP_HZ = 1000
)(
    input  wire start,                    // Start 2D search
    output reg  done,                     // Search complete
    output reg  [47:0] carrier_freq_word, // NCO word for current bin
    output reg  acq_start,                // Pulse to acquisition engine
    input  wire acq_done,                 // Acquisition complete
    input  wire [31:0] acq_peak_mag,      // Peak magnitude result
    output reg  [31:0] best_peak_mag      // Global best peak
);

// State machine: IDLE → CALC_DOPPLER → START_ACQ → WAIT_ACQ → COMPARE → NEXT_BIN → DONE
```

**Rationale:**
- **Autonomous Operation:** Hardware can search without CPU intervention
- **Deterministic Timing:** Predictable acquisition latency
- **Resource Efficient:** Only ~200 LUTs (pure FSM logic, no BRAM/DSP)
- **Production Ready:** Can be deployed in real hardware
- **Scalable:** Easy to add PRN loop for multi-satellite search

**Key Design Decisions:**

#### A. Synthesizable Doppler Calculation
```verilog
// Pre-computed constant for 1000 Hz step @ 200 MHz
// (1000 / 200,000,000) × 2^48 = 48'h00000053E2D623
wire signed [5:0] bin_offset = $signed(doppler_bin) - (NUM_DOPPLER_BINS / 2);
wire [47:0] calculated_word = bin_offset * 48'h00000053E2D623;
```

**Why Pre-Computed Constant?**
- Hardware divider is expensive (many DSPs, slow)
- Multiplication by constant is optimized by synthesis tool
- No rounding errors from runtime division
- Handles negative frequencies via 2's complement (`$signed()` cast)

#### B. Simple Start/Done Handshake
```verilog
input  wire start;      // Pulse high for 1 cycle to start
output reg  done;       // Pulses high when complete
output reg  busy;       // High while processing
```

**Why Not AXI4-Lite?**
- Overkill for acquisition (only need start/done)
- Adds significant RTL overhead (address decoder, register file)
- Parameters are fixed at synthesis time (no runtime config needed)
- Reserve AXI4-Lite for tracking channels (need runtime configuration)

#### C. Single-Cycle Start Pulse
```verilog
ST_START_ACQ: begin
    acq_start <= 1'b1;  // Assert pulse
    state <= ST_WAIT_ACQ;
end

ST_WAIT_ACQ: begin
    acq_start <= 1'b0;  // Clear pulse (1-cycle width)
    if (acq_done) state <= ST_COMPARE;
end
```

**Why Single-Cycle Pulse?**
- Matches acquisition engine's expected interface
- Prevents accidental double-triggering
- Clean, predictable timing
- Minimal logic overhead

**Trade-offs:**
- ✅ **Pro:** Fully autonomous (no CPU needed)
- ✅ **Pro:** Deterministic timing (~1.65 ms for 11 bins)
- ✅ **Pro:** Low resource cost (~200 LUTs)
- ✅ **Pro:** Production-ready RTL
- ❌ **Con:** Fixed search parameters (can't change at runtime)
- ❌ **Con:** Sequential search (not parallel)
- ❌ **Con:** Still requires DUT reset between bins (in current implementation)

**Simulation Results:**
```

Bin 1  (-4000 Hz): Peak = 519,946
Bin 2  (-3000 Hz): Peak = 519,946
Bin 3  (-2000 Hz): Peak = 519,946

Bin 5  (    0 Hz): Peak = 1,007,496  ← 🏆 WINNER
```

## 4. Doppler Search Controller Design

### Decision: 7-State FSM Architecture

**State Machine:**
```verilog
localparam [3:0] 
    ST_IDLE          = 4'd0,  // Wait for start
    ST_CALC_DOPPLER  = 4'd1,  // Calculate NCO word
    ST_START_ACQ     = 4'd2,  // Pulse acq_start
    ST_WAIT_ACQ      = 4'd3,  // Wait for acq_done
    ST_COMPARE       = 4'd4,  // Compare with global best
    ST_NEXT_BIN      = 4'd5,  // Increment bin counter
    ST_DONE          = 4'd6;  // Assert done, return to IDLE
```

**Design Rationale:**

#### A. Explicit State Encoding
- Use `localparam` for state names (self-documenting)
- Binary encoding (not one-hot) for resource efficiency
- 4 FFs for 7 states (vs 7 FFs for one-hot)

#### B. Sequential State Transitions
- Each state has a single, clear purpose
- No complex branching or parallel paths
- Easy to debug and verify

#### C. Global Peak Tracking
```verilog
ST_COMPARE: begin
    if (acq_peak_mag > best_peak_mag) begin
        best_peak_mag   <= acq_peak_mag;
        best_code_phase <= acq_code_phase;
        best_doppler_word <= carrier_freq_word;
    end
    state <= ST_NEXT_BIN;
end
```

**Why Track in Controller?**
- Acquisition engine only knows current bin's peak
- Controller maintains global best across all bins
- Simple comparison logic (just `>` operator)
- No need for complex sorting or priority encoders

#### D. Reset Behavior
```verilog
if (!rst_n) begin
    state           <= ST_IDLE;
    done            <= 1'b0;
    busy            <= 1'b0;
    acq_start       <= 1'b0;
    doppler_bin     <= 5'd0;
    best_peak_mag   <= 32'd0;  // Reset for new search
    // ...
end
```

**Why Reset `best_peak_mag` to 0?**
- Ensures any valid peak will be greater than initial value
- Prevents stale results from previous searches
- Simple, predictable behavior

**Trade-offs:**
- ✅ **Pro:** Clear, maintainable state machine
- ✅ **Pro:** Easy to add states (e.g., PRN loop)
- ✅ **Pro:** Minimal resource usage
- ❌ **Con:** Sequential processing (can't parallelize bins)
- ❌ **Con:** No early termination (always searches all bins)

**Rejected Alternative: Early Termination**
- **Idea:** Stop searching if peak exceeds threshold
- **Why Rejected:** Could miss better peaks in later bins
- **When to Use:** If search time is critical and threshold is well-calibrated

## 5. Parallel Processing Strategy Analysis

### Decision: Serial Doppler Search (Not Parallel)

**Options Evaluated:**

#### Option A: Fully Parallel (11 Parallel FFTs)
```
                    ┌─► [FFT IP 0 @ -5kHz] ─► [Peak Det 0] ─┐
                    ├─► [FFT IP 1 @ -4kHz] ─► [Peak Det 1] ─┤
  IF Data ──────────┼─► ...                                   ┼─► [Global Max]
  (broadcast)       └─► [FFT IP 10 @ +5kHz] ─► [Peak Det 10] ┘
```

**Resource Cost:**
| Resource | Per FFT IP | × 11 Parallel | Zynq-7020 Limit | Fits? |
|:---------|:----------:|:-------------:|:---------------:|:-----:|
| BRAM36 | 16 | **176** | 70 | ❌ **NO** (2.5× over) |
| DSP48 | 6 | **66** | 220 | ✅ Yes |
| LUTs | 3,000 | **33,000** | 53,200 | ✅ Yes |

**Verdict:** ❌ **Does NOT fit** on xc7z020

#### Option B: Partially Parallel (4 Parallel FFTs)
- 4 FFTs running in parallel
- Each FFT processes 3 Doppler bins sequentially (4 × 3 = 12 bins)
- **Speedup:** ~3× faster than fully serial
- **Resource:** 4 × 16 = 64 BRAM36 (✅ fits)

**Verdict:** ✅ **Feasible** but not chosen (complexity vs benefit)

#### Option C: Pipelined + Parallel Peak Detection
- Keep ONE FFT IP
- Pipeline stages: while bin N is in IFFT, bin N+1 is in FFT
- Store all peaks in parallel BRAM (11 × 4096 magnitudes)
- Use comparator tree to find global max in ~4 cycles

**Resource Cost:**
| Resource | Cost | Notes |
|:---------|:----:|:------|
| BRAM36 | +5 | Store 11 × 4096 magnitudes |
| DSP48 | +4 | Comparator tree uses subtractors |
| LUTs | +300 | Comparator tree logic |
| **Speedup** | **~2×** | Overlapping stages hides latency |

**Verdict:** ✅ **Best approach** for future optimization

#### Option D: Serial Search (Current Implementation)
```
Time ──────────────────────────────────────────────────►

Bin 0:  [Wipe] [FFT] [Mult] [IFFT] [Peak]
Bin 1:                              [Wipe] [FFT] [Mult] [IFFT] [Peak]
...
Bin 10:                                                                    [Wipe] [FFT] [Mult] [IFFT] [Peak]
```

**Resource Cost:**
- 1 FFT IP = 16 BRAM36
- Total = 16 BRAM36 (✅ fits easily)

**Performance:**
- 11 bins × ~150 µs/bin = ~1.65 ms
- Sequential bottleneck (can't process multiple bins simultaneously)

**Rationale for Choosing Serial:**
1. **Resource Constraint:** xc7z020 has only 70 BRAM36K
2. **Simplicity:** Easier to debug and verify
3. **Sufficient Performance:** 1.65 ms is acceptable for GNSS acquisition
4. **Future Upgrade Path:** Can add pipelining later if needed

**Trade-offs:**
- ✅ **Pro:** Fits on xc7z020 (critical constraint)
- ✅ **Pro:** Low resource usage (only 1 FFT IP)
- ✅ **Pro:** Simple, easy to debug
- ❌ **Con:** Slower acquisition (1.65 ms vs 0.15 ms parallel)
- ❌ **Con:** Sequential bottleneck

**Mitigation:**
- 1.65 ms is negligible compared to typical cold-start time (20-40 seconds)
- Can optimize later with pipelining if needed
- For most applications, serial search is fast enough

## 6. Doppler Step Size Strategy

### Decision: 1000 Hz Step (11 Bins) for Initial Implementation

**Search Grid:**
```
-5000  -4000  -3000  -2000  -1000   0  +1000  +2000  +3000  +4000  +5000
  |      |      |      |      |     |     |      |      |      |      |
  11 bins total, 1000 Hz spacing
```

**Rationale:**
- **FFT Resolution:** With 1ms coherent integration, frequency resolution is ~1000 Hz (1/T = 1/0.001)
- **Bin Spacing:** 1000 Hz matches FFT resolution (no oversampling)
- **Coverage:** ±5000 Hz covers typical GPS Doppler range
- **Speed:** 11 bins × 150 µs = 1.65 ms (fast enough)

**Alternatives Considered:**

#### Option A: 250 Hz Step (41 Bins)
```
-5000  -4750  -4500  ...  -250  0  +250  ...  +4750  +5000
  41 bins total
```

**Analysis:**
- **Time:** 41 bins × 150 µs = 6.2 ms (4× slower)
- **Resolution:** 250 Hz (4× finer)
- **Problem:** Oversampling! Adjacent bins are highly correlated (same sinc mainlobe)
- **Verdict:** ❌ **Wastes time** without real benefit

#### Option B: Two-Stage Coarse + Fine Search
```
Stage 1 (Coarse):  11 bins @ 1000 Hz step → Find peak at 0 Hz
Stage 2 (Fine):    21 bins @ 50 Hz step around coarse peak → Find peak at -25 Hz
```

**Analysis:**
- **Time:** (11 + 21) × 150 µs = 4.8 ms (3× slower than coarse-only)
- **Resolution:** 50 Hz (20× finer than coarse)
- **Benefit:** Much higher resolution with reasonable time cost
- **Industry Standard:** This is what u-blox, Qualcomm, GNSS-SDR do

**Verdict:** ✅ **Best approach** for future implementation

**Recommended Roadmap:**
1. **Phase 1 (Current):** 1000 Hz step, 11 bins (validate 2D search)
2. **Phase 2 (Next):** Add two-stage coarse+fine search
3. **Phase 3 (Optional):** Add parabolic interpolation for sub-bin accuracy

**Why 50 Hz Fine Step?**
- C/A code chip rate: 1.023 MHz
- 50 Hz Doppler error → 0.032 chips/sec code phase drift
- Over 20ms tracking update: 0.0006 chips drift (negligible)
- Tracking PLL can easily absorb this residual error
- Going finer (e.g., 10 Hz) gives diminishing returns

## 7. Multi-Channel Architecture Planning

### Decision: Time-Multiplexed Acquisition + Parallel Tracking

**Architecture:**
```
┌─────────────────────────────────────────────────────────┐
│  Shared Acquisition Engine (1x)                         │
│  - FFT-based parallel code search                       │
│  - Searches one PRN at a time                           │
│  - Controlled by doppler_search_controller              │
└────────────────────┬────────────────────────────────────┘
                     │
                     │ (PRN, Doppler, Code Phase results)
                     ▼
┌─────────────────────────────────────────────────────────┐
│  Tracking Channels (8x parallel)                        │
│  - Channel 0: PRN 1                                     │
│  - Channel 1: PRN 4                                     │
│  - Channel 2: PRN 12                                    │
│  - ...                                                  │
│  - Channel 7: PRN 31                                    │
└─────────────────────────────────────────────────────────┘
```

**Rationale:**
- **Acquisition is Sequential:** Only happens during cold start or signal loss
- **Tracking is Parallel:** Must track 8-12 satellites simultaneously for position fix
- **Resource Efficiency:** One acquisition engine serves all tracking channels
- **Time-Multiplexing:** Acquisition searches PRNs one by one (fast enough)

**Resource Budget (8-Channel Receiver):**

| Subsystem | BRAM36 | DSP48 | LUTs | FFs |
|:----------|:------:|:-----:|:----:|:---:|
| Acquisition Engine (1x shared) | 56 | 11 | 4,500 | 3,500 |
| Doppler/PRN Controller | 0 | 0 | 300 | 200 |
| Tracking Channels (×8) | 0 | 120 | 4,000 | 3,200 |
| Navigation Decoder | 2 | 4 | 1,500 | 1,500 |
| AXI4 Interface | 2 | 5 | 2,000 | 2,000 |
| **TOTAL** | **60** | **140** | **12,300** | **10,400** |
| **% of xc7z020** | **85%** | **63%** | **23%** | **10%** |

**Verdict:** ✅ **Fits comfortably** on Zynq-7020

**Key Insights:**

#### A. Acquisition is NOT the Bottleneck
- 32 PRNs × 1.65 ms/PRN = ~53 ms for full cold-start sweep
- Typical cold-start time: 20-40 seconds (dominated by nav bit decoding)
- Acquisition time is negligible (< 0.3% of total)

#### B. Tracking is Resource-Intensive
- Each tracking channel: ~15 DSP48, ~500 LUT
- 8 channels: 120 DSP48, 4,000 LUT
- This is the real resource consumer

#### C. BRAM is the Constraint
- Acquisition uses 56 BRAM36 (80% of total)
- Tracking uses 0 BRAM (uses distributed RAM)
- Code FFT ROM (32 PRNs) is the biggest BRAM consumer

**Multi-PRN Acquisition Strategy:**

**Option 1: Sequential PRN Search (Recommended)**
```verilog
// Modify doppler_search_controller to add PRN loop
for (prn = 1; prn <= 32; prn = prn + 1) begin
    prn_sel <= prn;  // Select PRN in code_fft_rom
    
    // Search all Doppler bins for this PRN
    for (doppler_bin = 0; doppler_bin < NUM_DOPPLER_BINS; doppler_bin = doppler_bin + 1) begin
        // ... existing Doppler search logic ...
    end
    
    // If peak found, hand off to tracking channel
    if (best_peak_mag > THRESHOLD) begin
        handoff_to_tracking(prn, best_doppler, best_code_phase);
    end
end
```

**Time Cost:**
- 32 PRNs × 11 bins × 150 µs = ~53 ms
- Very fast! Can search all 32 PRNs in < 100 ms

**Resource Cost:**
- 0 additional BRAM/DSP (just add PRN counter to FSM)
- ~50 additional LUTs

**Option 2: Parallel PRN Search (Not Recommended)**
- Instantiate multiple acquisition engines (one per PRN)
- **Resource Cost:** 32 × 56 BRAM = 1,792 BRAM (doesn't fit!)
- **Verdict:** ❌ **Impossible** on xc7z020

**Trade-offs:**
- ✅ **Pro:** Time-multiplexed acquisition is resource-efficient
- ✅ **Pro:** Can search all 32 PRNs in < 100 ms
- ✅ **Pro:** Leaves room for 8+ tracking channels
- ❌ **Con:** Sequential search (can't acquire multiple PRNs simultaneously)
- ❌ **Con:** Requires handoff logic to tracking channels

**Rejected Alternative: Parallel Acquisition**
- **Idea:** Instantiate 8 acquisition engines (one per tracking channel)
- **Why Rejected:** 8 × 56 BRAM = 448 BRAM (doesn't fit!)
- **When to Use:** If upgrading to xc7z100 (450 BRAM)

## 📊 Summary of Key Decisions (September 3, 2026)

| Decision | Choice | Rationale | Trade-off |
|:---------|:-------|:----------|:----------|
| Doppler Value | Corrected to 1 kHz (then verified 0 Hz) | Physically realistic GPS range | Required re-validation |
| 2D Search (Initial) | Testbench-driven | Easier debugging, rapid iteration | Not synthesizable |

| Multi-PRN Search | Sequential (loop through 32 PRNs) | Fast enough (< 100 ms), low resource cost | Can't acquire multiple PRNs simultaneously |

## 🎯 Design Philosophy Summary (September 3, 2026)

1. **Validate First, Optimize Later:** Get testbench-driven 2D search working before adding RTL complexity
2. **Resource-Conscious:** Every decision considers xc7z020 limitations (70 BRAM36K, 220 DSP48)
3. **Industry-Standard:** Follow proven GNSS receiver architectures (two-stage search, time-multiplexed acquisition)
4. **Incremental Development:** Build complexity layer by layer (single Doppler → 2D search → multi-PRN → tracking)
5. **Hardware-Efficient:** Leverage FPGA strengths (parallelism, pipelining, BRAM) while respecting constraints
